# ZZCall 公会战报归档

双击本目录的 **run.cmd**，选择 `1`，输入 `YYYY-MM-DD` 格式的 **UTC 日期**。
直接回车默认采集 UTC 昨天。首次运行需要下载物品名称字典；无需安装 Python 第三方包。
本机已用现有 Python 3.9 和 PowerShell 实测。工具只读取公开战报，不连接游戏客户端。

GitHub 只同步源代码、测试、配置、箱子排序表和 `data/ZZCall/results/日期/` 中你需要的最新结果。
原始响应、物品缓存、日报/周报中间数据、检查文件和历史快照保存在本地，不再纳入 Git。

## 同步范围

每个日期只同步最新一组以下文件，文件名仍包含日期、场次和生成时间：

- 彩色出勤 HTML。
- 每日出勤 CSV。
- 逐场出勤 CSV。
- 总补装采购 CSV（12u、14u 分场次，有其他场次时另列）。
- 合并的箱子补装 CSV。
- 总补装与箱子分配合一的补装网页 HTML（图标已嵌入）。

生成出勤/补装时会自动整理到 `data/ZZCall/results/日期/`，只替换该类旧结果，不影响另一类结果或其他日期。
旧结果若正在被 Excel/WPS 打开，暂留本地并提示；关闭文件后再次整理即可清理，新结果仍可正常生成。
同步目录之外的原始归档和旧版本仍在本地保留。结果目录不放 JSON、检查 TXT、缓存、原始响应或生成过程文档。
如需将已有归档整理为同步用结果，可运行 `py -3 publish_results.py`；该命令不会联网，也不会重新采集。
Git 提交只会包含允许跟踪的源代码、配置/箱子表和结果，不会自动上传本地归档。

## 看结果

以下是本地归档目录，供离线重新生成和核查，GitHub 不同步这些中间文件。每日数据：`data/ZZCall/daily/日期/`

- `report.txt`：汇总人数、逐人场次/天数/击杀/死亡、每场名单、完整性提示。
- `deaths.txt`：逐次死亡的中文装备、阶级和附魔（例如 6.2）、品质、数量。
- `equipment_totals.txt`：按物品编号和品质累计的装备数量。
- `report.json`：完整结构化报告。
- `attendance.jsonl`、`deaths.jsonl`、`equipment.jsonl`：每行一条 JSON，都是 UTF-8 文本，方便以后导入统计系统。
- `runs/运行时间/`：本次采集的独立快照，`raw/` 保留接口原始响应，方便核查。

周报：`data/ZZCall/weekly/周一日期/`，文件格式同上。
每次按日采集都会刷新那一周的汇总。也可以双击后选择 `2`，输入该周任意一天，只读取本地日报生成周报，不会联网补采。
一周按 UTC 周一至周日。缺少某一天的记录时会列出缺采日期，不能把缺采当成零参战。
要得到完整周报，请逐日采集该周七天；没有战报的日期也运行一次，保存已查询且无战报的记录。

## 统计口径

- 默认欧服、ZZCall、最低 10 人，与网站玩家战报页面的默认最低人数一致。
- **按每场战报里的 ZZCall 所属公会统计**，不是当前公会的全体成员。公会变化不会用今天的公会覆盖历史归属。
- 人员从 Details 的参战表读取，包含战报列出的零击杀、零死亡成员；公开战报没有记录的人无法推断是否到场。
- 跨 UTC 午夜的战斗全部归到开始日，因此次日凌晨的死亡也可能保存在前一天的日报里。
- 死亡从 Kills 的死者公会筛选，然后获取对应 Open 详情。重复运行按战报和 EventId 去重，不会把装备重复累计。
- 装备来自编号和中文物品字典，无需 OCR。`T6_…@2` 是 6.2；`Quality=4` 是卓越品质，两者单独记录。字典缺失的新物品尝试由游戏物品接口补全中文名。
- 保存十个穿戴槽位（主副手、头、衣、鞋、包、披风、坐骑、药水、食物），不统计背包库存。
- **这里的装备是死亡时穿戴快照，不表示实际掉落、损毁、被捡走或最终损失。**
- 接口未给 `Count` 时按单件穿戴物记 1，并在 JSON 中用 `count_reported=false` 标明；药水/食物有数量时保留接口数量。

## 完整性与重复采集

`complete` 表示本次发现的战报均采集成功，Kills 数量、公会汇总、成员死亡数量和装备详情通过核对。
这只代表当前数据源中的记录通过检查，不承诺网站没有漏收游戏事件。
`partial` 表示有请求失败、数量不符或名称未解析，请看 `report.txt` 的具体提示。
`provisional` 表示 UTC 当天还没结束，应在结束后重新采集。
网站近期战报也可能延迟更新，最好采集昨天的数据；必要时再次采集同一天。

每次运行都保留独立快照。如果已有 `complete` 日报，后续请求失败产生的非完整结果只保存在本次 `runs/` 中，原完整日报继续用于周汇总。
网络中断后重跑即可，历史文件保留。请求有间隔和有限重试，同一数据目录只允许一次采集/汇总运行。
公开接口可能限流、调整或不再保留较旧事件，建议及时逐日归档；缺失装备不会靠图片猜测补齐。

## 每日出勤与逐场明细

双击 `run.cmd` 后选 `4`，输入日期，从本地日报生成出勤名单；选 `1` 采集后也会自动生成。
结果在 `data/ZZCall/attendance/日期/生成时间/`，文件名包含日期和 UTC 生成时间：

- `出勤名单_日期_12u-14u_生成时间.html`：彩色网页，直接用浏览器打开，无需额外依赖。有“每日汇总”和“逐场明细”两个视图，可按玩家和角色筛选。
- `每日出勤_日期_12u-14u_生成时间.csv`：一人一行，分别列出 12u、14u 的出勤（1/0）和角色，最后为每日总场次。
- `逐场出勤_日期_生成时间.csv`：每场每人一条记录，包含角色、武器、击杀、死亡、IP、伤害和治疗量。
- `attendance.json`：对应的结构化数据、数据源时间与完整性信息。

**每日总场次只计 12u、14u 是否参与，同一时段多场战斗只计一次，最多 2 次。** 判定仍按战斗开始时间，12:00（含）至 13:00（不含）为 12u，14:00（含）至 15:00（不含）为 14u。
逐场明细保留当日报告的全部战斗；其他时段不计入每日出勤。只在其他时段出现的人不进入 12u/14u 汇总。
“未记录”/CSV 中的 0 表示对应时段的战报没有记录该人，不能证明他实际没有到场；未使用当前公会名单推断全会缺勤。

角色使用网站战报的 `role`：奶妈（healer）绿色，DPS（range/melee）红色，tank 蓝色，辅助（support）灰色，未识别角色显示“未知”。
同一人换角色时，每个时段保留所有记录到的角色，逐场明细保留当场角色。网页上方单列 12u/14u 奶妈名单。
CSV 本身不保存颜色，彩色标记在 HTML 中显示；阶段性日报和数据异常也会在网页中标明。
原有 `attendance.jsonl` 继续保留按战报累计的原始统计，新的每日 CSV/网页采用上述按时段去重口径。

## 补装采购与箱子分配 CSV

双击 `run.cmd` 后选 `3`，输入日期，从本地日报导出补装，不需要重新联网。
选 `1` 采集日报成功后也会自动导出补装。

输出使用 UTF-8 BOM CSV，保存在 `data/ZZCall/regear/日期/场次或合并场次/生成时间/`：

- `总补装_日期_12u或14u_生成时间.csv`：按物品编号（含阶级和附魔）及品质合计要买的件数。
- `箱子补装_日期_12u-14u_生成时间.csv`：合并当天 12u 和 14u，按人员汇总，每个人只有一行。
- `补装清单_日期_12u-14u_生成时间.html`：上方是总采购量，下方按当前箱子表的行列摆放个人补装；使用装备图标、P 等级和件数显示。

补装网页按装备种类和 P 等级累计，例如同一种装备的 T4.3、T5.2、T6.1、T7.0 均显示为 P7，不区分品质。采购 CSV 保留原有的具体物品/品质明细。
网页可在全部、12u、14u 之间切换，两部分数量同步变化；查找玩家只高亮格子，不改变箱子位置。
重复箱号、未匹配人员的装备放在待分配区，避免在候选箱子中重复摆放；管理的装备另列，仍计入总采购。
网页忽略箱子表行尾的多余空列，中间空格及行列编号保留。每次生成仍重新读取箱子表。
图标使用 [Albion Render 服务](https://forum.albiononline.com/index.php/Thread/131017-Update-on-API-New-Endpoints/)，首次生成需要联网下载，之后使用本地缓存；图标嵌入 HTML，打开网页无需再加载外部图片。
图片缓存位于本地 `cache/item_icons/`，不上传 GitHub。图标服务失败时仍保留名称和数量，并在网页检查提示中标明。

分箱表列为：箱子编号、玩家、分箱状态、主手、副手、头部、衣服、鞋子、披风、总件数。
每个装备栏使用 `P7 装备名 x2` 的格式；同栏多种物品用分号隔开。同一种装备按 `P=阶级+附魔` 合并，例如 T4.3、T5.2 均为 P7，忽略品质；不同装备种类或不同 P 等级分别记录。
分箱表不再显示日期 UTC、死亡次数、数据状态、品质、品质编号、箱子原名或逐次来源事件；日期和场次保留在文件名，原始分配明细保存在 `manifest.json` 中供核查。
采购总表仍按具体物品编号和品质列出采购需求。其他时段的分箱表单独生成，不混入 12u-14u。

场次按战斗开始时间判定，12:00（含）至 13:00（不含）UTC 为 `12u`，14:00（含）至 15:00（不含）UTC 为 `14u`。
例如 12:59 开始、13:01 发生的死亡仍归 12u。其他时段单独使用 `other-小时u`，不混入 12u/14u。
文件名中的生成时间为 UTC，以 `Z` 结尾。一天同一场次的多场战斗合并，同一 EventId 不重复计算，多次真实死亡则累计。

**只补主手、副手、头、衣服、鞋和披风，不补药水、食物、包和坐骑。** 各人的补装需求按死亡穿戴快照累计，尚未扣除个人存货、已回收物品或已发放补装。

箱子表默认在 `data/箱子排序.txt`，使用制表符保存网格，箱号为 `行-列`：例如第三行第一列为 `3-1`。
每次生成都会重新读取这份文件，更新名字或位置后再次导出即可。清空箱子时请保留制表符，不要把后面的格子左移。
名字忽略大小写和首尾空白；`config.json` 的 `box_aliases` 可记录简称对应的完整游戏名，其他至少三个字符的简称只在本日报人员中唯一前缀匹配时自动对应。
重复归属、有歧义的简称或名单中没有的人会列为待确认/待分配，不会猜箱号，也不会从采购数量中删掉。
`config.json` 的 `no_box_players` 列表用于管理等无需箱子的人员，目前为 `yanfang` 和 `ZZCall`。
这些人在分箱 CSV 中标为“管理（无需箱子）”，装备仍纳入总采购量和数量核对，不列入待分配警告。
例如 `TKU` 对应 `Tkulikus`，`xiaoye` 对应 `xiaoye007`，`mengxin` 对应 `Mengxin123`。
使用 Excel 导入时请把“箱子编号”列设为文本，避免把 `3-1` 自动显示成日期。

每次输出另附 `补装检查.txt`、`manifest.json` 和所用箱子表快照。合并分箱表按装备类型和 P 等级与对应场次采购表核对数量；待分配装备也纳入核对。
源日报未结束、装备缺失或箱号待定时，在采购表和检查文件中标记“待核对”；分箱 CSV 不包含数据状态列。

## 命令行

在本目录打开 PowerShell：

```powershell
py -3 collector.py --date 2026-10-30
py -3 collector.py --week 2026-10-30
py -3 collector.py --regear 2026-10-31
py -3 collector.py --attendance 2026-10-31
py -3 collector.py --regear 2026-10-31 --boxes "data/箱子排序.txt"
py -3 collector.py --date 2026-10-30 --refresh-items
py -3 -m unittest -v
```

修改 `config.json` 可以更换 `player` 和 `min_players`。也可使用 `--player`、`--min-players`。
同一周请使用相同最低人数口径，周汇总会拒绝混用筛选条件不同的日报。
Windows 默认通过 PowerShell 发 HTTPS 请求，本机直接 curl/urllib 访问 AlbionBB 会收到 403，而 PowerShell 可正常请求。
其他系统默认用 urllib，也可手动指定 `--transport urllib` 或 `--transport powershell`。
退出码：0=完整，2=部分/临时结果，1=错误，130=手动中断。

## 数据来源

- 网站与战报接口：[AlbionBB Europe](https://europe.albionbb.com/players/ZZCall/battles)。
- 装备详情备用源：[Albion Europe Gameinfo](https://gameinfo-ams.albiononline.com/api/gameinfo/events/455392129)。
- 中文物品字典：[ao-data/ao-bin-dumps](https://github.com/ao-data/ao-bin-dumps/blob/master/formatted/items.json)，本地精简缓存每七天更新；较早的 `broderickhyman` 仓库已归档，不再作为默认源。

不创建定时任务；每天由你点击运行。开发过程记录只保留在本地。
